Research Architect

Research Architect is my framework for building AI-assisted research systems for human teams. It converts a reviewed project design into an individual assistant kit for each participant. Every kit identifies its human operator, assigned workstream, methods, dependencies, and first action; the team then works through a shared system with review and handoffs.

The Hub coordinates the project; Spokes are the assistants assigned to individual team members; the Ingestor checks submitted work and reruns agreed steps when needed. Humans review contributions before reuse. Only the Hub publishes additions or corrections to the shared Library; Spokes and the Ingestor read approved material and send proposed changes back through review.

Research behind the architecture

A technical white paper and comparative literature review document the design. I reviewed thousands of research and technical sources and turned them into workflow instructions for citing evidence, comparing methods, surfacing conflicting findings, preserving uncertainty, and keeping a human reviewer responsible for decisions. This shaped the research process; it did not retrain the underlying AI models. The public literature review lists 25 cited entries; the broader source review informed the framework’s instructions and methods.

The guidance draws on research about data reuse, source tracking, scientific methods, and AI coordination. The current library indexes 134 sources and includes 38 local reference texts. Those counts describe available material, not 134 fully appraised papers. The new white paper covers the historical NWSW deployment, the current setup process, and the limits of adding a person or agent after a project has begun.

Continuity and review carried forward from RA 2.3

I carried the pilot’s continuity and recovery improvements into the generator for new Hub, Spoke, and Ingestor kits. I developed a local Doctor interface that runs selected diagnostic checks and keeps the reports, including a recovery route when an agent cannot start. These routine checks run without AI model calls.

An interruption can leave a team unsure whether an operation finished. I built records that keep finished, failed, and unknown outcomes distinct. I also developed updates that check the installed version and retain recovery history, and tested migration from saved RA 2.1 examples. Recorded human closure decisions take precedence over older imported states, keeping closed work from being silently reopened.

I built Library retrieval tools that retain the selected source version, related files, and later corrections. I separated routine message checks from full project restoration so a status check does not require loading the entire research history. When a result list is incomplete, the interface reports it. These working tools are carried forward into the current preview.

From an assignment to a reviewed handoff

I used Research Architect to generate the New World Screwworm coordination system, configured its deployment, and supported onboarding eight people. Versioned file lists, fingerprints, and separate approval, delivery, and acknowledgement records keep work traceable. The Spatial Evidence Workbench is my separate GIS application.

Inspect version and publication controls

Contributor packages list expected files and SHA-256 fingerprints to detect missing or changed contents. Version checks identify outdated starting checkpoints. Partial work is written separately, and the published copy is checked before it can replace the current version. Review, delivery, and acknowledgement records distinguish what was approved, sent, and received.

The framework is used in NWSW, where the RA 2.3 Hub/Library improvements are installed and tested. RA 2.5.1 is the separate current preview for creating kits. Shared context that develops through review

The review loop records findings, corrections, superseded assumptions, and unresolved questions. After human acceptance, authorized material is registered and published with exact versions, dependencies, and use limits. Participants retrieve relevant records for subsequent work; delivery and retrieval remain distinct from actually applying a correction.

Limitation: adding someone after the project starts

A new person and their new agent both need to catch up. The person must learn the project; the agent needs its decisions, evidence, terminology, dependencies, and unresolved work. Even an experienced team member introducing a fresh agent faces that agent’s context gap. A generated kit and Library access do not automatically transfer the established team’s working understanding.

The project keeps moving during onboarding. If new decisions and corrections accumulate faster than the newcomer can absorb them, the catch-up gap can persist. The lead and existing team must explain prior work, resolve misunderstandings, and check the new pair’s output; existing agents may also spend time and inference resources helping. That effort can slow the team and make late expansion impractical within its time and cost budget.

This is a limitation of the underlying AI technology and research workflow. Adding a kit does not guarantee more useful capacity, and reliable automatic late-stage onboarding has not been demonstrated. Feasibility depends on the role, project pace, and retained context. Restoring an established workstream is a different task.

Research that survives a new session

The system locates the designated current checkpoint and restores the required source context. RA 2.3 can reference exact duplicate material, reconstruct complete selected sources, and reuse retained context explicitly in the same conversation. Fresh or uncertain context is reconstructed; a disk check alone does not prove an AI assistant read it.

Set up the team without losing the decisions.

A team’s research question, responsibilities, methods, and approval decisions can otherwise remain scattered across setup conversations. I developed a setup record that retains answered questions and unfinished decisions between sessions, then connected it to checks before the supported kit build. A later session can continue from that recorded plan.

  • Work through the plan: 43 baseline questions and relevant follow-ups identify the team’s requirements.
  • Pause and return: recorded answers and unfinished questions remain available across sessions.
  • Review before building: the supported generator requires recorded preparation and approval for the exact configuration it will use.
  • Handle changes explicitly: changed answers keep their history and reopen affected decisions.

The recorded checks support the setup and build controls. They do not establish that an assistant always asks the right question or loads the correct saved state. In a later fresh-session and resume trial, the assistants omitted a required startup file before recovering through folder discovery. That known startup gap remains open; reliable automatic onboarding has not been demonstrated.

Make research guidance available when it is needed.

The package includes method guides, source references, and runnable examples using invented data. The examples show how repeated records can distort a comparison, how to evaluate a prediction without using the test answers during development, and when a result cannot be extended to an unsupported population.

I developed source retrieval that divides long references into manageable parts and checks that the parts reconstruct the complete selected text. Each part retains its source identity, so deeper material can be retrieved when needed. Local checks support file preservation and the example calculations; they do not establish better scientific judgment by every assistant.

Public technical example

Check the files yourself.

A handoff can look complete even when a file has changed. This small Python example compares two synthetic notes with a manifest of expected filenames and SHA-256 fingerprints, then demonstrates changed, missing, and unexpected files.

Created for this portfolio to make the method inspectable. It is a standalone demonstration, not a release of the RA runtime. A match establishes byte agreement with the supplied manifest; authorship, scientific validity, and approval require separate evidence.

Run the example and inspect the core check
  1. Extract the ZIP and open a terminal in the handoff-integrity folder. Python 3.10 or newer is the only requirement.
  2. Run python verify.py. The intact example reports that both files match the manifest.
  3. Run python verify.py --self-test. Five checks exercise intact, changed, missing, unexpected, and malformed inputs using temporary copies.

The byte-comparison function

This is the same function included in the download. The full script also checks the manifest structure and expected file list.

def inspect_file(path: Path, expected_hash: str) -> str:
    if path.is_symlink():
        return "REJECTED LINK"
    if not path.is_file():
        return "MISSING"
    digest = sha256()
    with path.open("rb") as stream:
        for block in iter(lambda: stream.read(1024 * 1024), b""):
            digest.update(block)
    return "MATCH" if digest.hexdigest() == expected_hash else "CHANGED"
