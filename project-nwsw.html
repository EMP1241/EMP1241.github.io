How the research system connects

A research network with shared memory.

I designed the coordination system so each round of research can build on the last. Contributions pass through Pod human review, Hub human review, and authorized Ingestor verification and reproduction, then return to the Hub for final human disposition. Accepted material is registered and published to the Library within its approved audience and use scope before later work retrieves it.

How the network learns from its work

This is iterative contextual learning: reviewed findings, corrected assumptions, accepted methods, and unresolved questions become part of the project’s cumulative memory. Later work can use that record when an agent retrieves current context. Corrections retain their history, including what was rejected or superseded and why.

The shared context improves what the agents have available to reason from. It does not retrain their underlying models or establish that every agent has read and applied each update. Delivery, acknowledgement, and actual use remain separate steps.

Read the review and reuse sequence
  1. Pod human review: the contributor reviews the evidence and reasoning, corrects issues, and records uncertainty before submitting.
  2. Hub human review: the project lead reviews scope, methods, and evidence and defines the checks required.
  3. Ingestor verification and reproduction: check file lists, versions, and hashes; rerun the specified reproducible steps within the authorized scope; report matches, discrepancies, and limits.
  4. Hub final acceptance: review the check results, accept or return the work, and specify its approved sharing scope.
  5. Library and reuse: approved versions become shared context. Contributors retrieve the current record for subsequent tasks. Material marked “Request from Hub” remains request-only.

This describes the review process. Completion and reproduction results are recorded for each contribution.

The question behind the maps

How do reporting practices, surveillance coverage, and changing map boundaries affect what the available New World Screwworm records can tell us? I bring sources into a common geographic and analytical framework so differences in reporting are not mistaken for differences in the underlying biology.

My role

I lead GIS development and the team’s research coordination: define evidence needs, reconcile reporting definitions, prepare reusable geography, connect records to the areas they describe, and integrate contributions into a shared comparison table. I build and maintain the software and delivery controls that keep source identities, method choices, contributor attribution, and unresolved gaps attached to the work.

From Research Architect to the project Hub

Research Architect is the reusable framework that turns a reviewed plan into individual AI assistant kits and shared research controls. I used it to generate the NWSW Hub, the project-specific system for assignments, incoming work, checkpoints, review, and handoffs. A checkpoint is a saved working state that a later session can recover.

The framework’s small HTML evidence interface lets the team inspect submissions, revisions, receipts, and originals. It is separate from the Spatial Evidence Workbench, the independent GIS application I built for mapped investigations and exports.

Keeping a growing research history usable

As the history grew, I added bounded context retrieval: a large lookup is delivered in manageable pages that retain the complete underlying record and its source references. The system checks that the parts reconstruct the original content. Publication also checks whether its starting checkpoint changed while work was underway, so an older session cannot silently publish over a newer state.

Current project-specific repairs preserve complete source text, raw transfer evidence, publication checks, and owner-closed decisions. The installed NWSW Hub and Library are maintained as their own versioned system; a new generic Research Architect release does not automatically upgrade the study or its contributors.

Complete evidence, without repeating the scan

The October 23 Hub update keeps long lookup results and message-check summaries complete. An assistant can read the next page of a retained result without running the lookup or scan again. Each lookup page keeps the source identity and review conditions attached, so a short display limit does not quietly remove findings.

Inspect the installed update and what the checks establish

Twelve targeted checks, an independent agent review of the exact files, and installed checks passed. A Unicode test reconstructed 297,516 characters across 188 pages. A real Library lookup retained all 11 sources; a message-journal fixture recovered its full 14,419-character summary instead of the earlier 640-character excerpt. Reading continuation pages triggered no new scan.

The installation preserved the active Hub, existing approvals and closed work orders, and all 24 protected file hashes. It improved evidence delivery without republishing the Library or replacing contributor kits. Extra deduplication produced no additional reduction on the already compacted Hub context, so the existing reader stayed in place.

A Library that preserves versions and use limits

I built shared Library infrastructure that keeps exact files, source references, package dependencies, corrections, and review history together. Following human acceptance, authorized material is registered and published for reuse within its recorded scope. A file can appear under several research topics while retaining one canonical identity and its dependency references. Contributors find the relevant version without loading the entire archive or creating competing copies.

“Available in Library” identifies stored files or verified aliases under their existing use limits. “Request from Hub” exposes reviewed discovery metadata for held material without releasing its payload. Publication checks and retained recovery records keep custody and availability distinct from scientific approval.

Testing spatial uncertainty at computational scale

I developed an exploratory location-uncertainty workflow with a documented 64-million-realization precision experiment: sixteen comparisons, with four million simulated realizations per comparison. Repeated sampling tested whether numerical estimates had settled under each specified model configuration.

Analytical comparisons and numerical checks supported precision within each configuration. They do not establish true event locations, geographic agreement across grids, or biological validation. This is a distinct experiment; its count is not a combined total of all project simulations.

A GIS workflow another person can rebuild

I built a scripted nine-stage ArcGIS workflow that reconstructs 16 linked GIS layers from a fixed, hash-checked input package. These layers include administrative boundaries, source-linked points, and separately categorized reporting areas; they are not 16 independent research findings. The build checks the licensed software environment, writes a log for every stage, stops if a stage fails, and confirms that the frozen inputs stayed unchanged.

The relocated package reopened in a fresh process, checking whether delivery depended on a hidden path or state on my computer. The recorded checks are available below.
