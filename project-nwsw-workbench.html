Spatial Evidence Workbench

I independently built the Workbench so a research map can retain the evidence and review history behind it. I designed the records connecting original files, map features, findings, and follow-up work, then built intake, saved investigations, and exports that preserve those connections. The local application is working; I am developing additional review and mapping features for version 0.3.

Why I built it

A map alone does not explain which source version, geographic boundaries, filters, or decisions produced it. I built the Workbench to retain that evidence alongside the map. My data model connects original files, extracted records, geographic features, and review decisions, while the interface lets a researcher inspect those relationships and save an investigation for later review.

My role

I independently designed and developed the application: its evidence model, spatial database integration, intake and validation workflows, browser interface, saved investigations, and export behavior. I maintain the system as the research requirements evolve.

Original evidence stays inspectable

I developed the intake workflow to preserve the original file and received version before creating searchable records or map features. I stored automated file checks, human intake decisions, and later research notes separately. A reviewer can therefore see both what arrived and which kind of review it received.

A spatial investigation with memory

I designed the relationships linking evidence records to map locations and shapes, then implemented them in PostGIS and the Leaflet interface. I built saved investigations that retain the selected sources, dated geographic boundaries, filters, and methods. A later reviewer can retrace that particular map with its original context.

Turn review findings into accountable follow-up

I extended the Workbench beyond intake into a review-and-follow-up workflow. A reviewer can identify a specific problem, attach supporting addenda, assign the next action with a due date, and retain notes and revision history. Conflicting edits are rejected instead of overwriting newer work.

Corrections keep the original evidence and identify the problem they address. An earlier decision can still apply when the evidence and the question being reviewed have not changed. Otherwise, the app keeps it as history rather than treating it as current approval. Unresolved file errors still block progress. I also built ZIP packages for individual recipients that preserve the selected versions and notes. The app records preparation and dispatch separately; users send the files themselves.

Inspect geographic layers without losing their source

I built a catalogue of map layers with separate controls, legends, source records, and notes explaining how records were linked to places. Researchers can download the part they selected. For grid-based data, I placed each cell using its geographic coordinates so the display keeps the data in the right location. Each layer retains its sources and mapping assumptions.

Engineering the handoff

I built the server-side file checks, data preparation, and export workflow in Python and FastAPI, with PostgreSQL/PostGIS storing the evidence and geometry. I connected those records to the browser using TypeScript and Leaflet. The export I designed carries the selected evidence, map area, methods, and review notes into the handoff, giving the recipient the basis for the result.

How I tested the review workflow

I tested bringing in evidence, following links between records and maps, reopening saved investigations, and exporting the work. I also checked conflicting edits and input-size limits. Those checks demonstrate the application’s handling of prepared examples. They do not measure sustained heavy use or judge the research conclusions.

Inspect functionality, capacity, and file-integrity checks

Functionality

I tested whether a reviewer could flag a problem, add a correction, keep a valid earlier decision, and hand off the next action without overwriting newer work. That pass included 535 Python tests, 57 frontend tests, and 42 browser workflows. Later mapping work added checks of layer-building tools, 65 frontend tests, and eight read-only browser workflows. Each pass covered a different stage of development.

Capacity boundaries

I tested eight server-request patterns across 3,998 evidence records and displayed 1,000 map points linked to 100 records, checking that a visitor could follow the points back to their evidence. Separate component tests covered 10,000 table rows, 5,000 map features, 250,000 coordinate positions, and 500 files in a ZIP. I checked that the next tested input beyond each limit was rejected. These were size-limit checks; I have not measured all those workloads running together.

File and display integrity

I checked that a walkthrough kept its 14 source-publisher records and 10 supporting research files identifiable, using receipt records and SHA-256 file fingerprints. I also compared the record inspector with a prepared table: all seven columns and all 472 rows appeared in the expected order. The purpose was to catch changed files or altered displays before someone relied on them.
