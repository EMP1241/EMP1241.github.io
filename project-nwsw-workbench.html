Why I built it

A map is only useful to a research team if the evidence behind it remains accessible. I built the workbench to keep original files, parsed records, spatial features, review decisions, and investigation scope together.

My role

I independently designed and developed the application: its evidence model, spatial database integration, intake and validation workflows, browser interface, saved investigations, and export behavior. I maintain the system as the research requirements evolve.

Original evidence stays inspectable

Intake keeps each original file and records which version was received before creating searchable evidence records or map features from it. Automated file checks, a person’s intake decision, and later research notes are stored separately, so a technical pass is not mistaken for scientific approval.

A spatial investigation with memory

PostGIS is the spatial database that links evidence records to map locations and shapes. The Leaflet map lets a researcher inspect those features. A saved investigation records which source files and dated boundary dataset were used, along with filters and methods, so a reviewer can retrace the map instead of receiving an unexplained picture.

Engineering the handoff

Python and FastAPI run the server-side file checks, data preparation, and exports. PostgreSQL/PostGIS stores evidence and map geometry; TypeScript and Leaflet connect that information to the browser. An export records its selected evidence, map area, methods, and review notes, so another person receives the basis for the map as well as the map itself.

How the software checks work

Different tests check different parts of the application. The server-side part of the application passed 399 automated Python tests. The browser interface had 26 automated tests, plus a TypeScript check for code and data-type mistakes and a build check to confirm the browser files could be assembled. A separate browser pass walked through 31 user workflows. These checks show that tested software paths behaved as expected; they are not a count of people or research findings.

Capacity checks used separate test inputs. Eight server-request profiles—the ways the browser asks the application for data—covered a combined 3,998 evidence records. A browser check displayed 1,000 map points connected to 100 underlying evidence records, checking both map rendering and the links back to those records. Other helper checks separately exercised up to 10,000 table rows, 5,000 map features (points or shapes), 250,000 coordinate positions, and 500 files in a ZIP archive. At each documented limit, the next tested input was rejected as expected. These separate boundary checks are not one combined performance test or proof of production-scale speed.

The walkthrough archive contains 14 source-publisher records and 10 supporting research files. Receipts record the files, and SHA-256 fingerprints act like digital checksums that can flag a changed file. In a prepared test dataset, the record inspector displayed all seven expected data columns and kept all 472 records in the same order as the map input. This checks that data stays intact as it is prepared for display; it does not establish that the original sources or research conclusions are correct.

Together, these checks show how specific parts of the software handled defined test cases. They do not validate the science, certify full production capacity, or measure real-world application speed.
