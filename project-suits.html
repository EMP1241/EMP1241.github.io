The problem

Astronaut fieldwork combines navigation, terrain awareness, equipment status, and scientific observation. For the Spacesuit User Interface Technologies for Students (SUITS) challenge, our Blinn College team proposed a mixed-reality interface that would bring those cues into the user’s view during simulated extravehicular activity (EVA).

About NASA’s SUITS student challenge ↗

My role

I led the team and served as its primary system designer. I developed the navigation and display concepts, connected the proposed sensing and positioning components, and helped document the design and its evaluation plan. The accompanying concept deck credits me for its concept art and interpretation.

Two scales of navigation

For local positioning, the original proposal placed Bluetooth Low Energy (BLE) tags on wearers and fixed telemetry spikes at known locations. The spikes would receive tag signals, use received signal strength (RSSI) to estimate distances, and combine those estimates through trilateration. The interface would present waypoint bearing, distance, and relative height using a compass-style display and spatial anchors.

For nearby terrain, the design explored infrared time-of-flight and LiDAR depth sensing to communicate changes in surface shape and obstacles. These were proposed inputs to the HoloLens 2 interface. I envisioned a light triangulated irregular network (TIN) overlay following the surface, intended to make slopes, edges, and depressions easier to interpret in shadow. The concept material does not establish a measured positioning accuracy or an implemented sensor-fusion system.

A larger crew-positioning grid

The overhead illustration explores a modernized version of the idea: a 300 × 300 m work area with 16 fixed spikes at 100 m intervals. Small crew-position markers convey the scale. Nearby anchors would support a position estimate for each wearer; the grid would feed those estimates into the command hub for distribution across the work area. The 100 m spacing is an illustrated layout, not a measured coverage or accuracy result.

This extension uses Bluetooth Channel Sounding, which derives distance information from signal phase and round-trip timing, rather than the original proposal’s RSSI method. The layout is illustrative; hardware, terrain visibility, anchor geometry, and positioning performance would require testing. It does not establish lunar coverage or an implemented upgrade.

A command hub keeps the shared map current

The intended design included a central command hub that would maintain the latest crew positions and shared waypoints, then distribute changes to connected headsets. The positioning grid would supply ongoing updates, allowing the system to refresh the team’s shared map as astronauts moved.

Known spike locations would establish one coordinate system for the work area. The hub would distribute each wearer’s identity, coordinates, and update time to connected headsets. A headset would compare its own position and viewing direction with those received coordinates to place a teammate’s marker, bearing, and distance. This is how the concept would show a teammate beyond direct BLE contact with the wearer: the position arrives through the shared network.

New waypoints and pins would return to the hub and become part of the same shared map. Timestamps would distinguish a recent update from a last-reported position during a connection loss. The illustrations describe this information flow; the network transport, update rate, and performance still require specification and testing.

Waypoints, teammates, and shared pins

The intended setting was lunar fieldwork in low visibility. An astronaut should be able to identify a destination, locate another crew member, and return to a location pinned by the wearer or a teammate. Marker shape, labels, direction, distance, and relative height would help distinguish those cues in the display.

The original concept deck used annotated visual references to explain waypoint behavior. The illustration above reconstructs that interface idea using a lunar setting and shared markers. The broader proposal also included suit-status information, geological photographs and annotations, and collaboration with a remote expert.

Making the proposal testable

The evaluation plan connected interface choices to observable tasks: following a route, completing instructions, recognizing terrain shapes, and using voice controls under background noise. Proposed measures included accuracy, completion time, and user feedback. These are evaluation plans from the proposal, rather than reported trial results.

What this work demonstrates

The completed artifacts show how I translate an operational problem into a system design, explain interface behavior visually, coordinate a student team, and define questions that human testing could answer. The original proposal and deck are retained as project records; the public excerpts omit personal contact information.
